## Components +80

### Компонент Router +20

Я реализовала простой клиентский роутер на чистом TypeScript без использования фреймворков. Основная цель этого компонента — организовать навигацию в одностраничном приложении (SPA), сопоставляя URL-пути с функциями рендеринга.

Oтказ от использования готовых библиотек был осознанным решением: это позволило лучше понять базовые механизмы работы маршрутизации в браузере и глубже разобраться в принципах построения SPA.
Мы могли бы также использовать React Router, Page.js, Navigo.js.

#### Основные моменты
Класс Router отвечает за:
- хранение и управление списком маршрутов
- обработку событий браузерной навигации
- рендеринг нужного представления в зависимости от URL
- базовую защиту маршрутов (auth guard)

#### Архитектурные решения
Маршруты описываются с помощью типа Route, который включает:
- path — строковый путь
- render — функцию, отвечающую за отрисовку
- protected (опционально) — флаг, указывающий, требуется ли авторизация

В конструктор передаются:
- Массив маршрутов
- Функция isAuth, определяющая, авторизован ли пользователь

Такой подход демонстрирует принцип внедрения зависимостей (dependency injection), что делает компонент гибким и независимым от конкретной реализации авторизации.

#### Основная логика работы
1. Инициализация
- Метод init():
  - подписывается на событие popstate (навигация назад/вперёд)
  - подписывается на DOMContentLoaded (первичная загрузка страницы)
  - сразу вызывает обработку текущего маршрута
Это обеспечивает корректную работу роутинга как при первой загрузке, так и при навигации через браузер.
2. Навигация
- Метод navigate(path):
  - использует history.pushState для изменения URL без перезагрузки страницы
  - вручную вызывает обработку маршрута
Это стандартный подход для SPA, реализованный без сторонних инструментов.
3. Обработка маршрута
- Метод handleLocation():
  - Получает текущий путь
  - Ищет соответствующий маршрут
  - Обрабатывает три сценария:
    - Маршрут не найден
    Отображается простая страница 404
    - Закрытый маршрут без авторизации
    Пользователь перенаправляется на главную страницу
    - Корректный маршрут
    Вызывается функция render

#### Плюсы решения
- Простота
Компонент намеренно реализован без фреймворков, чтобы продемонстрировать понимание базовых механизмов браузера (History API, события, работа с DOM).
- Чистая архитектура
Логика маршрутизации отделена от логики авторизации.
- Гибкость и расширяемость
Благодаря простому интерфейсу маршрутов компонент легко доработать под более сложные сценарии.
- Понимание фундаментальных принципов
Изучила как работают роутеры “под капотом”, а не только умение пользоваться готовыми решениями.

#### Ограничения и возможные улучшения
Tекущая реализация — это минимально жизнеспособная версия (MVP), и её простота является частью учебной цели.
Потенциальные улучшения:
- поддержка динамических маршрутов (например, /quiz/:id)
- работа с query-параметрами
- более продвинутая обработка 404
- поддержка асинхронного рендеринга
- расширяемая система guards (например, роли пользователей)

### Dashboard and filters form +20
В рамках проекта я реализовала Dashboard и форму фильтрации без использования фреймворков, на чистом TypeScript и нативных DOM API. Такой подход был выбран осознанно: он позволил сфокусироваться на базовых механиках работы браузера, управлении состоянием и разделении ответственности между частями приложения.

Несмотря на внешнюю простоту, компоненты решают реальные задачи и демонстрируют понимание ключевых принципов построения интерфейсов.

#### Dashboard
Компонент Dashboard выполняет роль точки входа в пользовательский сценарий после авторизации.

#### Сильные стороны

Компонент отвечает только за отображение и пользовательские действия (навигация, logout), не смешивая бизнес-логику.
- Интеграция с роутером
Вся навигация делегируется Router, что делает архитектуру предсказуемой и расширяемой.
- Контроль состояния авторизации
Через setAuth реализовано явное управление состоянием пользователя без скрытых зависимостей.
- Простота и прозрачность
Вся логика компонента легко читается и не содержит “магии”, что важно для поддержки и отладки.

#### Filters Form
Форма фильтрации — более сложный компонент, который связывает UI, преобразование данных и состояние приложения.

#### Сильные стороны
- Динамическая генерация интерфейса
Форма строится на основе конфигурационного объекта (filterOptions), что упрощает масштабирование и изменение структуры.

Снижает дублирование кода и делает создание DOM-элементов более декларативным.

Использование функций toCategory, toLevel, toMode показывает понимание необходимости отделения “сырого” пользовательского ввода от доменной логики.
- Контролируемое управление состоянием
Логика работы с состоянием прозрачна:
  - очистка предыдущего состояния (clearQuiz)
  - установка нового (updateQuiz)

- Предсказуемый поток данных
Поток “пользовательский ввод → преобразование → обновление состояния” реализован последовательно и явно.
- Базовый UX (обратная связь)
Всплывающее уведомление после применения фильтров улучшает пользовательский опыт без усложнения архитектуры.

#### Плюсы
Важно подчеркнуть, что простота реализации в данном случае — это не ограничение, а осознанный инженерный выбор:
- Понимание основ вместо абстракций
Компоненты реализованы без фреймворков, что демонстрирует знание того, как работают UI и роутинг “под капотом”.
- Контроль над поведением приложения
Нет скрытых механизмов — вся логика находится под полным контролем разработчика.
- Лёгкость отладки и поддержки
Прямолинейная архитектура упрощает поиск ошибок и внесение изменений.
- Хорошая база для масштабирования
Текущая структура уже содержит разделение на слои (UI, state, utils), что облегчает дальнейшее развитие.

#### Ограничения и как зона роста
- работа напрямую с DOM (можно инкапсулировать глубже)
- отсутствие реактивности
- глобальное состояние можно структурировать лучше
- управление событиями может усложниться при росте проекта

### Компоненты Loader и Quiz Screen +20
Pеализовала простой, но переиспользуемый компонент загрузки (Loader) и интегрировала его в экран викторины (Quiz Screen). Несмотря на минималистичность, это решение покрывает важный сценарий асинхронной загрузки данных и демонстрирует понимание пользовательского опыта.

#### Loader
Функция renderLoader создаёт и возвращает DOM-элемент индикатора загрузки.
Сильные стороны:
- Инкапсуляция UI-элемента
Loader реализован как отдельная функция, которую можно использовать в разных частях приложения без дублирования кода.
- Разделение структуры и стилей
Вся логика отображения (анимации, внешний вид) вынесена в CSS, а TypeScript отвечает только за структуру. Это правильное и масштабируемое разделение.
- Переиспользуемая утилита (createElement)
Упрощает создание DOM-элементов и делает код более декларативным и читаемым.
- CSS и кастомная анимация без библиотек
Спиннер реализован через @keyframes и псевдоэлементы, что показывает понимание работы CSS-анимаций.
- Производительность
Использование transform: rotate() — это хороший подход, так как он оптимизирован браузерами.
- Базовая доступность
Текст "Loading" скрыт визуально, но остаётся доступным для скринридеров.

#### Quiz Screen (интеграция Loader)
Компонент quizScreen показывает, как Loader используется в реальном сценарии.

Логика работы
- Создаётся контейнер
- Проверяется наличие данных в состоянии (currentQuestions)
- Если данные уже есть:
  - викторина рендерится сразу
- Если данных нет:
  - отображается Loader
  - запускается асинхронная загрузка данных (quizQuestionsService)

#### Плюсы решения
- Условный рендеринг на основе состояния
Нет лишней загрузки — если данные уже есть, пользователь сразу видит результат.
- Прогрессивный UX
Пользователь мгновенно получает визуальную обратную связь (Loader), а не “пустой экран”.
- Разделение ответственности
Чётко разделены:
  - отображение (Loader)
  - контейнер экрана
  - загрузка данных
- Неблокирующий асинхронный вызов
Использование void подчёркивает, что загрузка не блокирует рендеринг.
- Переиспользуемость
Loader можно легко применять в любых других асинхронных сценариях.

#### Возможные улучшения
- явное управление жизненным циклом Loader (появление/скрытие)
- обработка ошибок при загрузке
- добавление ARIA-атрибутов (например, aria-busy)
- более реактивный подход к обновлению UI

### Design Patterns +10

1. Dependency Injection - передача зависимостей извне делает компонент расширяемым и тестируемым:
`constructor(routes: Route[], isAuth: () => boolean)`

2. Single Responsibility Principle (из SOLID)
Router — только маршрутизация
Loader — только отображение загрузки
FiltersForm — только ввод и трансформация данных

3. Factory-функция для создания DOM-элементов.
`createElement(...)`

4. State Management (упрощённый state pattern / store)
`updateQuiz(...)`
`clearQuiz()`

5. Guard (Router) - Route Guard pattern
`if (route.protected && !this.isAuth())`

### API Layer: Выделение слоя работы с API (изоляция от UI компонентов) +10
- UI / Presentation Layer (Dashboard, quizScreen, renderQuiz)
renderQuiz — точка входа для отображения теста, отвечает только за “сборку” интерфейса, не загружая данные самостоятельно.
quizScreen — отвечает за визуальное представление: показывает вопросы и контейнер для навигации.
Компоненты UI не знают о том, как загружаются или сортируются вопросы. Они просто получают уже подготовленные данные.
- API / Data Layer (quizService, filterQuestions, quizQuestionsService)
quizService — загружает все вопросы из JSON, выполняет парсинг и трансформацию данных.
quizQuestionsService — применяет фильтры (selectedCategory, selectedLevel), перемешивает массив, выбирает количество вопросов в зависимости от режима.
UI не знает про fetch, shuffle или фильтрацию — оно получает готовые данные.
- State Layer (getQuiz, updateQuiz, setIndex, setCurrentRoute)
Управляет глобальным состоянием викторины: выбранные категории, уровень, текущий вопрос.
Изолирует состояние от компонентов, чтобы UI мог перерисовываться при изменениях.
- Routing Layer (Router, renderQuiz back button, popstate)
Отвечает за навигацию между страницами (/dashboard, /quiz).
Реализован через pushState, hash и popstate.
UI вызывает навигацию через router.navigate, но не управляет историей напрямую.
