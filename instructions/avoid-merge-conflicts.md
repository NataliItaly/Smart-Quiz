# Как избежать merge conflicts

## Bы отправляете pull request и CI workflow процесс завершился неудачей

Локально у вас может не быть oшибок , husky pre-commit разрешил выполнить commit.
**Если CI упал, значит код объективно не проходит проверки, даже если husky пропустил commit**

Почему husky пропустил, а CI — нет:

1. oшибки появились ПОСЛЕ коммита:
  - commit
  - смержил develop или подтянул изменения
  - появились конфликты / типовые ошибки
**Husky проверял старое состояние, а CI — уже новое**

2. Разные версии зависимостей - В CI (чистая среда):
- свежий npm install
- возможно другая версия TypeScript
- другие eslint rules
**локально всё закэшировано - ошибки могут не проявляться**

3. Husky мог не выполниться - commit cделан с `--no-verify`

**Если CI упал kод нельзя мержить независимо от того, что было локально**


## Что можно сделать:

1. Обновить develop
```git checkout develop
git pull origin develop
```
**Это гарантирует, что у тебя локально актуальный develop**

2. Перейти в свою ветку
`git checkout your-branch`

3. Подтянуть изменения из develop:
Есть два варианта:
  3.1. Вариант 1
`git merge develop`

#### Что происходит:

- Git берёт последние коммиты develop и сливает их в твою ветку.
- Если есть конфликты → Git попросит их разрешить.
- История сохраняется как есть, появляется merge-коммит, если нужно.

Пример схемы:
```develop:   A --- B --- C
feature:        D --- E
merge:          D --- E --- M
```
M = merge-коммит


- Merge-коммит фиксирует объединение
- Можно увидеть, что изменения из develop добавились к твоей ветке
- Твои коммиты не переписываются
D и E остаются без изменений
- Merge безопасен, не ломает твою ветку
- Линейная история HE сохраняется
Если хочешь чистую линейную историю, используют git rebase develop

  3.2. Вариант 2 (чище история)
`git rebase develop`

#### Что происходит:

Git берёт твои коммиты D и E и “переписывает их”, ставя поверх последнего коммита C из develop.
Если есть конфликты → их нужно вручную разрешить.

Пример схемы:
```develop:   A --- B --- C
feature:        D --- E
rebase:          D' --- E'
```
D', E' = переписанные коммиты (хеши новые)
История становится линейной, без merge-коммитов
**Опасно делать на публичной ветке, которую кто-то уже вытянул**

#### Потенциальный риск переписывания твоих изменений при rebase
Команда ```git rebase develop```
Берёт твои коммиты из feature-ветки и “накладывает” их на последние коммиты develop.
В процессе могут возникнуть конфликты, которые нужно будет вручную разрешить.

Изменения не пропадут, Git их не перепишет без твоего участия.
Но если кто-то внёс изменения в develop в тех же файлах, где ты работал, Git попросит разрешить конфликт.

То есть:
**Rebase не стирает твои коммиты, он просто переносит их на новую “базу”.**
**Merge аналогично добавляет изменения develop в твою ветку, но оставляет “дерево” коммитов нетронутым.**


4. Решить конфликты (если появятся)

5. Запустить проверки
```npm run check```

6. Запушить
```git add .
git commit -m "merge develop + fix conflicts"
git push
```

## Hе делай так:
git pull origin develop  (находясь в своей ветке)

По умолчанию ```git pull = git fetch + git merge```
Git пытается влить удалённый develop в твою feature-ветку, как merge.
Это неправильно:
1. Ты не работаешь напрямую с удалённым develop:
Если ты выполняешь:

```git checkout feature/my-feature
git pull origin develop
```
Что делает Git:
- Делает git fetch origin develop → забирает удалённый коммит C (или новые коммиты, если были)
- Делает merge этих коммитов в твою ветку feature

*То есть ты не обновляешь локальный develop, а сразу вливаешь чужие изменения в свою feature-ветку.*
Это нарушает порядок: твоя feature-ветка “обходит” локальный develop.
Результат: трудно понять, что было добавлено develop, а что твои изменения.

2. История “путается”:
Представим, что после твоих коммитов D и E в develop кто-то сделал новый коммит F:

```origin/develop: A --- B --- C --- F
feature:               D --- E
```
Если ты делаешь ```git pull origin develop```

История после pull будет примерно так:

```A --- B --- C --- F
           \
            D --- E
                 \
                  M   <-- merge-коммит автоматически создан Git
```
Появляется лишний merge-коммит M, который объединяет твои D/E и удалённый F
История не линейная, сложно проследить порядок изменений

3. Если кто-то другой уже сделал merge → появляется лишний merge-коммит:
Допустим, у кого-то другая feature-ветка была слита в develop:

origin/develop: A --- B --- C --- F --- G
feature:               D --- E
Ты снова делаешь:
git pull origin develop
Git создаёт новый merge-коммит H в твоей feature:
```A --- B --- C --- F --- G
           \
            D --- E
                 \
                  H
```
Merge-коммит H лишний, история усложняется
Если бы ты сделал сначала:
```git checkout develop
git pull origin develop
git checkout feature
git merge develop
```
Merge-коммит появился бы на feature, но с локально обновленным develop, проще отслеживать изменения


### Локальная подготовка перед коммитом
Всегда перед началом работы обновляй свою ветку разработки:
git checkout develop
git pull origin develop
git checkout feature/my-feature
git rebase develop   # или merge develop, если предпочитаешь merge
